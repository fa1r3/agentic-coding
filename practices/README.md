# The f3 practices catalog

Know-how that `f3 init` draws on, by project type and stack: rules written into `AGENTS.md`, skills copied into the project, recipes that pre-fill the Stack section, archetypes that frame the project type. The design notes are in `REFERENTIEL-PRATIQUES.md` at the root of the toolkit; this file describes the format of an entry.

`install.sh` links this folder to `~/.local/share/f3/practices/`, where the agents read the body of an entry. `f3 practices` reads it from the toolkit, and the tests of the toolkit check it (`node --test cli/test/*.test.mjs`).

## Layout

```
practices/
├── catalog.md               generated by `f3 practices catalog`: one line per entry
├── archetypes/<id>/ENTRY.md project types
├── recipes/<id>/ENTRY.md    stack recipes
├── rules/<id>/ENTRY.md      short rules written into the Adopted practices section of AGENTS.md
└── skills/<id>/SKILL.md     know-how copied into .claude/skills/<id>/ of the project, with its other files
```

The folder of an entry is named after its `id`. Every entry is written in English: it is copied as is into the project, next to the invariant part (D23). After changing a header, run `node cli/f3.mjs practices catalog > practices/catalog.md`.

## Header

A header between two `---` lines, in a subset of YAML: scalars, nested mappings, lists (`[a, b]` or `- item` lines), and folded block scalars (`key: >`).

Common to every entry:

| Key | Meaning |
|---|---|
| `id` | kebab-case, unique in the catalog; a skill starts with `f3-stack-`: a skill of f3, chosen by the stack of the project; no skill or command of the toolkit takes this prefix (D13) |
| `kind` | `archetype`, `recipe`, `rules` or `skill`, as its folder |
| `version` | `x.y.z`; raise it at every change of the text copied into a project |
| `status` | `stable`, or `draft`: listed as not available and never proposed (D25) |
| `summary` | one sentence |
| `applies-when` | criteria, below; absent: the entry fits every project |
| `requires`, `conflicts` | entries that must, or must not, be adopted with this one |

Criteria of `applies-when`, a closed vocabulary (D20). Each one is an option of `f3 practices select`, whose value the architect takes from the validated answers of the interview. A criterion absent from an entry does not filter; a fact not given checks nothing, and the output says so.

| Criterion | Option | Values |
|---|---|---|
| `archetypes` | `--archetype` | ids of archetypes; ignored with `--archetype none` |
| `ui` | `--ui` | `yes` (the product has a user interface) or `no` |
| `languages` | `--language`, repeatable | languages of the stack, lower case: `typescript`, `python`… |
| `frameworks` | `--framework`, repeatable | frameworks of the stack, lower case: `angular`, `fastify`, `electron`… |
| `contracts` | `--contract`, repeatable | forms of the contracts the project publishes, lower case: `openapi`, `asyncapi`, `protobuf`… |
| `exposure` | `--exposure`, repeatable | `none` (no network), `private` (a private network, the local machine), `public` (the internet) |

By kind:

- **archetype**: `invariant` (how it applies the invariant part, without exception, D5), `interview` (at most 3 questions), `recipes`, `practices` (rules entries), `skills` (generic skills only, valid whatever the frameworks the project chooses; a skill of a framework is proposed by its `applies-when`, never by an archetype), `workflow-impact` (each key names the sub-section of the Stack section it feeds, D26: `modules`, `enforcement`, `entry-points`, `ui`, `transport`, `verification`, `e2e`, `observation`). Body: when to choose it, when not to, known pitfalls.
- **recipe**: `check` (what the web research must verify before proposing it, D9). Body: a draft of the Stack section, one sub-section per heading of the template of `agents-md.md`, which the architect adapts.
- **rules**: `code` (2 to 4 capital letters, unique: the rules are numbered `<code>-1`, `<code>-2`…, D19; a number removed by a new version is never given again), `title`, `size-budget` (maximum lines of the body, D11), `pairs-with` (skills that detail them, D10). Body: 3 to 10 numbered rules, each with its reason and an example when two readings are possible, independent of any technology.
- **skill**: `name` (its id) and `description` (when to load it: the tools load a skill by its description, D24), `loaded-by` (the agents concerned, for the reader only). Body and other files: the skill, copied with only `name`, `description` and its `source` line in its header (D17, D27).

The global budget of the Adopted practices section is `GLOBAL_BUDGET` in `cli/lib/practices.mjs`.
