# End-to-end test practice

## Vocabulary

- **End-to-end test**: a test that drives the launched application, as the user would, and proves a scenario of the specs. It never reads the code of the application and imports nothing from it.
- **Feature file**: the Gherkin translation of the spec of one capability, generated by the f3-features script. Its scenarios are the scenarios of the specs, word for word.
- **Step definition**: the code bound to one step sentence. It is written once and serves every scenario that uses the sentence.
- **Page object**: a class that represents one view of the interface. Its methods are the actions the view offers; its accessors are the information it shows and its states.
- **Component object**: a class that represents a component shared by several views, such as a confirmation dialog.
- **Test entry point**: a means provided by the application code to drive it in test (launch in test mode, test data, replaced native dialog). It prepares data or replaces an external dependency (a native window or dialog, the clock, an external service); it never changes how a processing of the application runs. It is described in the design.md of the change that created it and built by the developer.
- **Manual scenario**: a scenario listed in `tests/e2e/manual-scenarios.md`, which is not automated end to end. See Manual scenarios.
- **Delta of the change**: the requirements the change adds, modifies, removes or renames, as listed by the f3-features script.
- **Impacted view**: a view listed in the Impact section of the change's ux.md.
- **Views register**: `ux/views.md`, the list of the views present in the code, with their displays (route and kind) and the screens seen through each, written by the developer. It is the only source of the names of views for the end-to-end tests.

## Organization

The end-to-end test project lives in `tests/e2e/`:

- `features/`: the feature files, one per capability, generated by `node ~/.local/share/f3/scripts/f3-features.mjs <change-id>` and versioned. They are never edited by hand: a scenario changes in the specs, then the files are regenerated. The test code the runner generates from them is not versioned.
- `steps/`: the step definitions, one file per business concept of `CONTEXT.md`, named after its English term.
- `pages/`: one page object per view, in a file named after the view (`pages/invoice-editor.ts` for the view `invoice-editor`). Component objects are in `pages/components/`, named after the component.
- `support/`: the launch of the application in test mode, the test data builders that use the test entry points, and the fixtures that give step definitions their page objects.

The runner, its configuration and the four commands ("generate the tests", which fails and lists the steps without definition, "export the step catalog", "run the whole suite", "run one capability") are in the End-to-end tests subsection of the Stack section of `AGENTS.md`.

## Scenarios not automated yet, during a migration

When an adopted project rewrites its existing scenarios slice by slice, a capability can hold scenarios whose steps have no definition yet, and generation would fail for the whole suite. During this migration only, the End-to-end tests subsection of the Stack section may set the runner to generate such a scenario as skipped (`fixme`) instead. Then:

- every scenario of the delta of the change must be automated: a scenario of the delta skipped for a missing step is a failure of the pass;
- a scenario outside the delta skipped for a missing step is not a failure: it is counted by capability and written in the report, never ignored;
- `BACKLOG.md` keeps an entry for the rewriting of the scenarios still skipped. The change that automates the last of them sets the runner back to failing the generation.

## Manual scenarios

A scenario is automated end to end, unless the only way to reach its starting state or trigger its action is a test entry point that changes how a processing runs (for example holding a task halfway). In that case only, and with the user's agreement, it is listed in `tests/e2e/manual-scenarios.md`:

- f3-features tags it `@manual` in its feature file, which stays the complete translation of the specs; the runner excludes the tag from generation and every run, as the Stack section says; no step definition is written for it;
- its rule is proven as its entry says: unit or integration tests written by the developer, and a check by hand of what remains visible, made by the user when checking the journeys;
- an entry that matches no scenario any more makes f3-features fail: the change that renames or removes the scenario updates the entry.

An entry is proposed by the Test member of Tres Amigos or by the tester at acceptance, and written with the user's agreement by the analyst or the tester; an amendment may change it. A listed scenario is not raised again as an objection about its automation.

Format of the file:

~~~markdown
# Manual scenarios

Scenarios of the specs that are not automated end to end, decided with the user.

## <capability> › <requirement> › <scenario>

- Reason: <the test entry point the scenario would need, and why it would change how a processing of the application runs>
- Replacement coverage: <the unit or integration tests that prove its rule, and what the user checks by hand>
- Origin: <change-id>, <tres-amigos or acceptance>, <date as YYYY-MM-DD>
~~~

Example, fictional invoicing project, not to be reused:

~~~markdown
## invoicing › Issue an invoice › Issuing refused while the yearly closing is running

- Reason: the starting state needs a yearly closing held halfway; holding it would pause the closing process in test mode.
- Replacement coverage: unit tests of IssueInvoice with a double of the ClosingStatus port that reports a closing in progress; the user checks by hand that the refusal message is displayed.
- Origin: add-yearly-closing, tres-amigos, 2026-03-10
~~~

## Writing step definitions

1. **The expectation comes from the step sentence, and from it alone.** A step definition does exactly what its sentence says, no more, no less. You never deduce an expectation from what the application shows.
2. **Variable data are parameters.** A quoted text or a number of the sentence is a parameter of the definition, so that the definition serves every scenario that uses the sentence.
3. **Through page objects only.** A step definition never locates an element itself: it calls page objects and component objects. GIVEN steps prepare the starting state through the test data builders of `support/` when a test entry point exists; otherwise through page objects.
4. **THEN steps assert.** Assertions that wait (an expectation on a locator) are written in THEN step definitions, never in page objects, and never with a fixed wait in milliseconds.
5. **Each scenario prepares its own data** and depends neither on another scenario, nor on the order of execution, nor on the state left by a previous scenario.

## Writing page objects

1. **One page object per view, with the name of the view in `ux/views.md`.** A view that has no page object yet gets one when a scenario first needs it. A view the scenarios go through that is absent from the register cannot get a page object: report it as a deviation for the developer.
2. **Methods are the actions of the view; accessors are its information and its states.** A state of the view (named by its screens `<view>/<state>` in the register, or described by the specs: empty, loading, error) has an accessor named after the state.
3. **Locate by accessible role and name only** (role, label, text), in this order of preference. Never a CSS class, a DOM structure or a technical identifier. An element that has no usable role or accessible name is an accessibility deviation: report it.
4. **A page object contains no assertion about an expected result.** It may wait until its view is displayed.
5. **Discover the interface on the running application, never in its code**, with the means described in the Observing the running application subsection of the Stack section.
6. **Native windows and dialogs go through test entry points.** If none exists for a scenario, the scenario cannot be automated: report it as a deviation for the developer. If the only possible test entry point would change how a processing of the application runs, propose instead an entry in the manual scenarios register.

## Example

Fictional invoicing project using Playwright and playwright-bdd: not to be reused.

Generated `tests/e2e/features/invoicing.feature`:

~~~gherkin
# Generated by f3-features from the OpenSpec specs. Do not edit: regenerate.

Feature: invoicing

  Rule: Issue an invoice

    Scenario: Issuing refused for a line without amount
      Given a draft invoice "F-2024-002" for the customer "Dupont"
      And the invoice "F-2024-002" has a line "Consulting" without amount
      When the accountant opens the invoice "F-2024-002"
      And the accountant issues the invoice
      Then the issuing is refused with the reason "A line has no amount"
      And the invoice "F-2024-002" has the status "draft"
~~~

`tests/e2e/pages/invoice-editor.ts`, page object of the view `invoice-editor`:

~~~ts
import type { Locator, Page } from '@playwright/test';

export class InvoiceEditor {
  constructor(private readonly page: Page) {}

  async open(invoiceNumber: string): Promise<void> {
    await this.page.goto(`/invoices/${invoiceNumber}`);
    await this.page.getByRole('heading', { name: `Invoice ${invoiceNumber}` }).waitFor();
  }

  async issue(): Promise<void> {
    await this.page.getByRole('button', { name: 'Issue' }).click();
  }

  status(): Locator {
    return this.page.getByRole('status');
  }

  // State issue-error of ux.md.
  issueError(): Locator {
    return this.page.getByRole('alert');
  }
}
~~~

`tests/e2e/steps/invoice.ts`, step definitions of the concept Invoice:

~~~ts
import { expect } from '@playwright/test';
import { Given, When, Then } from '../support/fixtures';

Given('a draft invoice {string} for the customer {string}', async ({ testData }, invoiceNumber: string, customer: string) => {
  await testData.draftInvoice(invoiceNumber, customer);
});

When('the accountant opens the invoice {string}', async ({ invoiceEditor }, invoiceNumber: string) => {
  await invoiceEditor.open(invoiceNumber);
});

When('the accountant issues the invoice', async ({ invoiceEditor }) => {
  await invoiceEditor.issue();
});

Then('the issuing is refused with the reason {string}', async ({ invoiceEditor }, reason: string) => {
  await expect(invoiceEditor.issueError()).toHaveText(reason);
});

Then('the invoice {string} has the status {string}', async ({ invoiceEditor }, invoiceNumber: string, status: string) => {
  await invoiceEditor.open(invoiceNumber);
  await expect(invoiceEditor.status()).toHaveText(status);
});
~~~

The last definition opens the invoice named by the sentence before reading its status: without that line, it would check the status of whatever invoice is displayed, which is not what the sentence says.

## Classifying a failure

For each scenario that fails, establish the facts before proposing anything:

- does the f3-features report list its requirement in the delta of the change (added, modified or renamed)?
- does it go through an impacted view?
- what is the error message, and what does the screenshot or the trace show?

Then propose an outcome; the user decides:

| Facts | Usual proposal |
|---|---|
| Requirement in the delta | Adapt the test (new or changed steps, page objects), or a ticket for the developer if the application does not do what the scenario asks |
| Requirement unchanged, scenario goes through an impacted view | Adapt the page object of that view only: the view was redesigned. Never change a step definition or the scenario for this reason |
| Requirement unchanged, no impacted view | Regression: a ticket for the developer. Never change a test to make it pass |
| Defect that exists outside the scope of the change | Backlog entry |
| The scenario cannot be automated as written, or its data are inconsistent | Amendment of the spec, following the Amendments section of the spec-practice skill: a rewording that keeps what the scenario proves, or that says explicitly what it no longer proves |

A change to a shared step definition outside the scenarios of the delta always appears in the report, with its reason.

## Acceptance report

One report per pass, in `openspec/changes/<change-id>/acceptance/pass-<NN>.md`, where `<NN>` follows the last existing number, on two digits. A pass never modifies the report of a previous pass. Format:

~~~markdown
# Acceptance of change <change-id>, pass <NN>

- Date: <YYYY-MM-DD HH:MM>
- Tested commit: <short hash>
- Conclusion: <"green" if every scenario passes, except the scenarios outside the delta skipped during a migration, and no decision is pending, otherwise "red">

## Delta

<the delta of the change as listed by f3-features>

## Tests

- Steps added: <sentences, or "none">
- Steps changed: <sentences, with the reason, or "none">
- Page objects added or changed: <names, or "none">
- Scenarios run: <number>, passed: <number>, failed: <number>
- Skipped for a missing step, outside the delta: <number per capability, or "none">
- Manual scenarios of the delta: <their identifiers, or "none">

## Fidelity review

<the findings of the independent review of the new and changed step definitions and page objects, and what was corrected, or "No finding.">

## Failures and decisions

| No. | Scenario | Facts | Proposal | Decision |
|---|---|---|---|---|


## Tickets

<the tasks added to tasks.md under "Acceptance fixes, pass <NN>", or "none">

## Backlog

<the entries added to BACKLOG.md, or "none">

## Amendments

<the numbers of the amendments of tres-amigos.md made during this pass, or "none">
~~~

A scenario is identified as `<capability> › <requirement> › <scenario>`. A table without row contains the single line "None.".
